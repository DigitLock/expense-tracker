**Date:** 2026-06-16
**Scope:** DISCOVERY only — no code/proto/migration/config changes, no commits.
**Subjects:** expense-tracker (ET) ↔ currency-rate-service (CRS, `github.com/DigitLock/currency-rate-service`).
**ET currency convention (target state):** `rate = RSD per 1 foreign unit`; `amount_base` stored in RSD.

## TL;DR — the 5 open spec questions answered

| # | Question | Answer |
|---|----------|--------|
| 1 | One call (all pairs) or per-pair? | **Both available.** `GetRates` = batch (one base + N targets, one call). `GetRate` = single pair. `ListSupportedPairs` = config list. Recommended: one `GetRates(base="RSD", targets=["EUR","USD"])` call. |
| 2 | Which pairs are served now? | **RSD→EUR, RSD→USD, EUR→USD** (3 active pairs). Note direction: base→target only; **no `*→RSD` pairs exist**. |
| 3 | latest-only or history + date? | Service keeps **full history** (append-only `rates`), but the gRPC API returns **latest-only** per pair, with an `updated_at` timestamp on each rate. |
| 4 | How is "rate unavailable" expressed? | **Two mechanisms.** (a) `GetRate` → gRPC **`NotFound`** status (pair not configured / no rate data). (b) `GetRates` → missing targets are **silently omitted** from the `rates` array (partial success). Plus a per-rate **`is_outdated` bool** flag for stale-but-present rates. |
| 5 | Does response carry source/provider? | **Yes** — `Rate.source_provider` (e.g. `fawazahmed0`, `frankfurter`). Can populate ET `source` column directly instead of a fixed literal. |

## A. Currency Rate Service contract (.proto)

**Proto path:** `/Users/digitlock/Documents/Projects/currency-rate-service/proto/currency_rate/v1/service.proto`
**Package:** `currency_rate.v1` · **go_package:** `github.com/DigitLock/currency-rate-service/internal/grpc/pb`
**Service:** `CurrencyRateService` · **gRPC port:** `50052` · **Auth:** none (public data) · **Reflection:** enabled.

### A.1 RPC methods & messages (verbatim from proto)

```proto
service CurrencyRateService {
  rpc GetRate(GetRateRequest) returns (GetRateResponse);
  rpc GetRates(GetRatesRequest) returns (GetRatesResponse);
  rpc ListSupportedPairs(ListSupportedPairsRequest) returns (ListSupportedPairsResponse);
}

message Rate {
  string from_currency = 1;
  string to_currency = 2;
  double rate = 3;
  google.protobuf.Timestamp updated_at = 4;
  bool is_outdated = 5;
  string source_provider = 6;
}

message CurrencyPair {
  string from_currency = 1;
  string to_currency = 2;
  int32 polling_interval_seconds = 3;
  bool is_active = 4;
}

message GetRateRequest  { string from_currency = 1; string to_currency = 2; }
message GetRateResponse { Rate rate = 1; }

message GetRatesRequest  { string base_currency = 1; repeated string target_currencies = 2; }
message GetRatesResponse { repeated Rate rates = 1; }

message ListSupportedPairsRequest {}
message ListSupportedPairsResponse { repeated CurrencyPair pairs = 1; }
```

- **`rate` is `double`** (float64) — ET stores `DECIMAL(15,6)`. Conversion float→decimal happens client-side in ET.

### A.2 One call vs per-pair
- `GetRates` returns **multiple** rates for one base currency in a single call → use this.
- `GetRate` returns **one** pair.
- **Pairs actually served now (live):** `RSD→EUR`, `RSD→USD`, `EUR→USD` — confirmed via `ListSupportedPairs` and DB `currency_pairs` (all `is_active=true`, polling 3600s).

### A.3 latest-only vs history / date
- API exposes **latest rate per pair only** (`GetLatestRate` server-side). No history RPC.
- Each `Rate` carries **`updated_at`** (`google.protobuf.Timestamp`) = when the rate was fetched from the provider (DB `rates.fetched_at`).
- History exists in the service DB (`rates` append-only) but is not surfaced over gRPC.

### A.4 "Rate unavailable" in the contract — CRITICAL for partial success
From `internal/grpc/server.go`:
- **`GetRate`**:
  - missing/empty args → `InvalidArgument`
  - invalid code format (`^[A-Z]{3,5}$`) → `InvalidArgument`
  - pair not configured → **`NotFound`** "currency pair X→Y not configured"
  - configured but no rate row yet → **`NotFound`** "no rate data for X→Y"
- **`GetRates`** (batch): invalid/unconfigured/no-rate targets are **`continue`-skipped** → **omitted from the response array, no error**. Caller MUST diff requested vs returned `to_currency` to detect gaps.
- **Staleness:** present-but-stale rates are still returned with **`is_outdated=true`** (proto3 omits the field when `false`). Staleness ≠ unavailability.

### A.5 Source/provider
- `Rate.source_provider` is populated (DB `providers.name`). Observed values: `fawazahmed0` (RSD↔EUR, RSD↔USD), `frankfurter` (EUR↔USD).
- **Recommendation:** map `source_provider` → ET `exchange_rates.source` (better provenance than a fixed `'currency-rate-service'`). Optionally prefix, e.g. `crs:fawazahmed0`.

### B.3 Direction per pair — `rate` = **"target per 1 base"** (i.e. `1 from = rate × to`)
| Pair (from→to) | Observed rate | Reads as | Plausibility |
|---|---|---|---|
| RSD→EUR | 0.008503294 | 1 RSD = 0.0085 EUR | 1/0.0085 ≈ **117.6 RSD per EUR** ✓ |
| RSD→USD | 0.0098757819 | 1 RSD = 0.00988 USD | 1/0.00988 ≈ **101.3 RSD per USD** ✓ |
| EUR→USD | 1.1607 | 1 EUR = 1.16 USD | ✓ (ECB/Frankfurter) |

> **CRS direction is the INVERSE of ET's convention.** CRS gives `target per 1 base` (RSD→EUR = 0.0085). ET wants `RSD per 1 foreign` (EUR→RSD = 117.5). **The sync MUST invert.**

### B.4 Mapping formula → ET convention (`rate_ET = RSD per 1 foreign`)
| ET row needed (from→to) | Source from CRS | Formula |
|---|---|---|
| EUR→RSD (RSD per EUR) | CRS `GetRate(RSD,EUR)` = `r_re` | **`rate_ET = 1 / r_re`** (e.g. 1/0.008503294 ≈ 117.60) |
| USD→RSD (RSD per USD) | CRS `GetRate(RSD,USD)` = `r_ru` | **`rate_ET = 1 / r_ru`** (e.g. 1/0.0098757819 ≈ 101.26) |
| EUR→USD / USD→EUR (no RSD) | CRS `GetRate(EUR,USD)` = `r_eu` | direct `r_eu`, or inverse `1/r_eu` — **but ET schema can't store either today** (see C.3) |

- ET's existing reports use `GetLatestRate(from=<foreign>, to="RSD")` then `amount_base / rate`. So storing `EUR→RSD = 117.5` and `USD→RSD = 101.3` plugs into Reports unchanged. Inversion at sync time is the safe choice.

## C. ET `exchange_rates` schema (repo + DB facts)

> **Note on migration 011:** `011_add_user_role` does **NOT** touch `exchange_rates`. The `exchange_rates` schema comes solely from **`006_create_exchange_rates_table`**. (The "watch 011" hint does not apply — there is no 011 exchange-rates migration.)

### C.1 Exact schema (migration 006 + sqlc model)
| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `id` | `UUID` | NOT NULL | `gen_random_uuid()` | PK |
| `from_currency` | `VARCHAR(3)` | NOT NULL | — | CHECK ∈ {RSD, EUR} |
| `to_currency` | `VARCHAR(3)` | NOT NULL | — | CHECK ∈ {RSD, EUR} |
| `rate` | `DECIMAL(15,6)` | NOT NULL | — | "1 from = rate × to" (1 EUR = 117.50 RSD); CHECK `rate > 0` |
| `date` | `DATE` | NOT NULL | — | rate validity day (column is **`date`**, not `rate_date`/`effective_date`) |
| `source` | `VARCHAR(100)` | NOT NULL | `'manual'` | provenance |
| `created_at` | `TIMESTAMP` | NOT NULL | `CURRENT_TIMESTAMP` | insert time (≠ `date`) |

sqlc model `ExchangeRate`: `Rate decimal.Decimal`, `Date pgtype.Date`, `Source string`. There is **no `fetched_at`/`is_outdated`/`updated_at`** column in ET — CRS staleness/age metadata has nowhere to land today.

### C.2 Unique / constraints (DDL verbatim)
```sql
CONSTRAINT exchange_rates_from_currency_check  CHECK (from_currency IN ('RSD', 'EUR')),
CONSTRAINT exchange_rates_to_currency_check    CHECK (to_currency   IN ('RSD', 'EUR')),
CONSTRAINT exchange_rates_rate_positive        CHECK (rate > 0),
CONSTRAINT exchange_rates_currencies_different  CHECK (from_currency != to_currency),
CONSTRAINT exchange_rates_unique_date          UNIQUE (from_currency, to_currency, date)
```
Indexes: `idx_exchange_rates_date (date DESC)`, `idx_exchange_rates_currencies_date (from_currency, to_currency, date DESC)`.
- **Upsert key** = `(from_currency, to_currency, date)`. ET already has `UpsertExchangeRate` keyed on this conflict target.

### C.3 Can it represent a non-RSD pair (e.g. EUR↔USD)? — NO
- **USD is rejected** by both CHECK constraints (`IN ('RSD','EUR')`). So **RSD↔USD and EUR↔USD cannot be stored at all** without a migration loosening the CHECKs.
- Only **RSD↔EUR** is representable today.
- **Silent-breakage risks for Reports if data is mis-synced:**
  1. **Direction trap:** if CRS's `RSD→EUR = 0.0085` is inserted as ET `from=EUR,to=RSD` **without inverting**, Reports computes `amount_base / 0.0085` → ~13,800× inflation. Must invert (B.4).
  2. **USD requests:** Reports already accepts `?currency=USD` but no USD row can exist → permanent fallback-to-RSD (`currency_note`). Enabling USD requires a CHECK migration **and** a decision on EUR↔USD storage (C.3 / open decision 1).

## D. Wiring CRS proto into ET

### D.1 Current ET proto/buf setup
- **`buf.yaml`** (v2): single module `path: proto`; lint STANDARD; breaking FILE.
- **`buf.gen.yaml`** (v2): plugins `protoc-gen-go` + `protoc-gen-go-grpc`, both `out: internal/grpc/pb`, `opt: paths=source_relative`.
- **`proto/`**: `accounts.proto`, `transactions.proto` — **flat layout, no package subdirs, no `option go_package`** lines (generation relies on `paths=source_relative` + flat files → `internal/grpc/pb/*.pb.go`).
- **`internal/grpc/pb/`**: `accounts.pb.go`, `accounts_grpc.pb.go`, `transactions.pb.go`, `transactions_grpc.pb.go`.
- ET is currently only a gRPC **server** (its own services). For CRS it needs a generated **client** stub.

> Layout mismatch to note: CRS proto uses a versioned package dir (`currency_rate/v1/service.proto`) with an `option go_package` pointing at the **CRS** module. ET's flat, `go_package`-less convention differs — vendoring the file as-is into ET's flat `proto/` needs care (the `go_package` option would emit into the CRS import path, not ET's).

### D.2 Options to obtain the CRS stubs in ET

**Option 1 — Vendor the `.proto` into ET and generate locally.**
- Copy `service.proto` into ET (e.g. `proto/currency_rate/v1/service.proto`), let ET's buf generate the client stub into `internal/grpc/pb/...`.
- ➕ ET owns generation; consistent toolchain; no cross-repo Go dependency; works offline; client+server from same `buf generate`.
- ➖ Proto duplicated across repos → drift risk (must re-copy on contract change); must reconcile the versioned dir + `option go_package` with ET's flat/no-go_package convention (likely set ET's own `go_package` or restructure ET pb output); adds a `google/protobuf/timestamp.proto` well-known-type dependency (buf provides it).

**Option 2 — Import CRS's pre-generated Go stubs as a module dependency.**
- `go get github.com/DigitLock/currency-rate-service`, import `.../internal/grpc/pb`.
- ➕ Zero proto duplication; always matches CRS's released contract.
- ➖ **Blocker:** stubs live under `internal/` in CRS → **not importable** by ET (Go `internal/` rule). Would require CRS to move pb to a public path and cut releases. Couples ET build to CRS's full module/deps. Not viable without CRS changes.

**Option 3 — Buf remote (BSR) / `buf generate` against the remote module.**
- ➕ Single source of truth, versioned.
- ➖ Requires CRS published to BSR (not set up); network dependency; heaviest setup.

**Recommendation: Option 1 (vendor the proto + local codegen).** Fastest, no upstream changes, matches ET's existing buf workflow. Mitigate drift by (a) copying the proto verbatim under a `currency_rate/v1/` path, (b) adding ET's own `go_package`/output handling so stubs land in `internal/grpc/pb`, (c) a short note/checklist to re-sync on CRS contract bumps. Revisit Option 2/3 only if CRS exposes a public stub package or BSR module.

## Открытые решения для архитектора

### (1) Как хранить EUR↔USD (пара без RSD)
- ET `exchange_rates` **сегодня физически не может** хранить ни USD, ни EUR↔USD (CHECK ∈ {RSD,EUR}). Reports-конвертация тоже завязана на `from=<foreign>, to='RSD'`.
- Варианты:
  - **(1a) Только RSD-пары (минимальный sync):** синхронизировать лишь RSD↔EUR (и RSD↔USD после расширения CHECK), EUR↔USD не хранить; кросс-курсы при необходимости считать через RSD. Минимальная миграция (добавить USD в CHECK). Сохраняет инвариант "всё через RSD", который любит Reports.
  - **(1b) Хранить произвольные пары:** расширить CHECK до {RSD,EUR,USD}, разрешить EUR↔USD строки. Тогда нужно ревизовать Reports (он ищет только `*→RSD`), иначе EUR↔USD-строки просто не используются (тихо).
- **Рекомендация к обсуждению:** 1a — расширить CHECK на USD, хранить `USD→RSD` (инверсия CRS `RSD→USD`), EUR↔USD не персистить в ET; так Reports остаётся "RSD-центричным" без переписывания. Требует решения архитектора.

### (2) Показывать ли возраст курса (`fetched_at`) в Reports
- CRS отдаёт `updated_at` + `is_outdated`. ET-таблица **не имеет** колонки под это (есть только `date` (день) и `created_at` (момент вставки)).
- Варианты: (2a) игнорировать — хранить только `date`; (2b) добавить колонку `fetched_at TIMESTAMPTZ` (+ возможно `is_outdated`) миграцией и прокидывать в Reports (например пометка "rate as of …" / "stale"); опереться на уже существующее в Reports поле `currency_note` для предупреждения о staleness.
- **Решение архитектора:** нужна ли пользователю видимость свежести курса в отчётах (влияет на миграцию схемы).

### (3) Форма ответа "курс недоступен"
- Со стороны CRS: `GetRate` → `NotFound`; `GetRates` → **молчаливое отсутствие** target в массиве; `is_outdated=true` для устаревших.
- Открытые решения для ET-стороны sync/Reports:
  - Как трактовать `is_outdated=true`: принимать курс или отвергать/помечать?
  - При batch `GetRates`: явно диффать запрошенные vs полученные target'ы (иначе пропуск пары пройдёт незамеченным).
  - Поведение Reports при отсутствии курса уже определено (fallback RSD + `currency_note`) — нужно решить, отличать ли "нет пары" от "курс устарел" в этом сообщении.
