# v0.4.0 — st1 Discovery: gRPC Method Implementation Audit

**Date:** 2026-06-19 · **Branch:** main · **Tag baseline:** v0.3.0
**Scope:** AUDIT ONLY — no code/proto/sqlc/config changes. Goal: close the 5 open spec
questions (§8) and map where business rules are enforced, ahead of implementing the 14
remaining gRPC methods.

## TL;DR — biggest GAPs / risks

- **No Create/Update/Delete protos exist.** Only `List*` RPCs are defined for Account &
  Transaction; `categories.proto`, `reports.proto`, `auth.proto` do **not exist**. All 12
  non-List RPCs need new proto messages + regen. (R1)
- **Business rules live in REST handlers**, not below them, for: initial_balance ≥ 0,
  currency match, category-type match, category hierarchy/parent rules, and delete-guards.
  Thin gRPC handlers are impossible for these without extracting a shared service layer. (R2)
- **Account name uniqueness (ALREADY_EXISTS) is enforced nowhere** — no DB constraint, no
  repo check, no REST check. Spec rule unimplemented. (decision needed)
- **No domain→gRPC-status mapping helper**, and only `users.go` has sentinel errors;
  account/transaction/category repos return raw pgx/sqlc errors (not-found = string
  `"no rows in result set"`). A unified error helper must be built. (R-err)
- Balance trigger is correct for soft-delete (excludes `is_active=false`, fires on UPDATE). (R3 = OK)

## 1.3 Update* messages — partial-update field typing

**None of `UpdateAccountRequest`, `UpdateCategoryRequest`, `UpdateTransactionRequest` exist.**
There is nothing to audit for `optional`/wrapper typing — they must be designed from scratch.
This is decision **R1**: the REST layer already does true partial updates via Go pointers
(`*string`, `*bool`, `*uuid.UUID`, `pgtype.Text`, plus a `ClearParent bool`). To preserve
partial-update semantics over gRPC, the new `Update*` messages MUST use `proto3 optional`
(or `google.protobuf.*Value` wrappers) on every mutable field — a bare scalar cannot
distinguish "set to zero/empty" from "leave unchanged".

Repository update inputs that the proto must mirror:

| Repo input | Optional fields (partial) | Special |
|------------|---------------------------|---------|
| `UpdateAccountInput` | `Name *string`, `Description pgtype.Text`, `IsActive *bool` | balance not updatable (trigger-owned) |
| `UpdateCategoryInput` | `Name *string`, `ParentID *uuid.UUID`, `IsActive *bool` | `ClearParent bool` to null the parent → needs explicit proto signal |
| `UpdateTransactionInput` | (see §3) account/category/type/amount/currency/description/date | currency must re-match account |

# 2. gRPC Server: Registration & Interceptors

File: `internal/grpc/server.go` (`NewServer`).

| Aspect | Finding |
|--------|---------|
| Registered services | `pb.RegisterAccountServiceServer` (NewAccountHandler), `pb.RegisterTransactionServiceServer` (NewTransactionHandler); `reflection.Register` enabled |
| Interceptor chain | `grpc.ChainUnaryInterceptor(interceptors.LoggingInterceptor(), interceptors.AuthInterceptor(jwtService))` — order: **logging → auth** |
| Auth context keys | `interceptors.ContextKeyUserID`, `interceptors.ContextKeyFamilyID` (typed `contextKey string`); values are `uuid.UUID` from JWT claims (`claims.UserID`, `claims.FamilyID`) |
| Accessor | `interceptors.FamilyIDFromContext(ctx) (uuid.UUID, bool)`; **no UserID accessor exists yet** (needed for transaction CreatedBy/audit) |

**Coverage of new services:** the chain is registered **globally on the `grpc.Server`**, so
every service registered on it (including new ones) is covered automatically. No per-service
interceptor wiring is needed. New handlers just call `FamilyIDFromContext`. ⚠️ For
TransactionService.Create the handler also needs `user_id` — add a `UserIDFromContext`
accessor (the value is already in context, only the helper is missing).

# 4. Business-Rule Map (where enforced)

| Rule | Enforced at | Proof | Below handler? |
|------|-------------|-------|----------------|
| Account name uniqueness (ALREADY_EXISTS) | **NOWHERE** | no UNIQUE in `003_create_accounts_table.up.sql`; no `23505`/`ALREADY_EXISTS` in `accounts.go`/repo | ❌ **unimplemented** |
| initial_balance ≥ 0 | **REST handler** | `internal/api/handlers/accounts.go:113` (validation error); no DB CHECK on `initial_balance` | ❌ REST-only → must port |
| Balance recalc on tx create/update/delete | **DB trigger** | `trigger_transactions_update_balance AFTER INSERT OR UPDATE OR DELETE` (migr 005); fn `update_account_balance()` (migr 010) | ✅ below — reused free |
| → trigger reacts to soft-delete (UPDATE is_active=false)? | **YES** | fn sums `WHERE t.is_active = true` (migr 010 line 34) and trigger fires on UPDATE → inactive rows excluded on recalc | ✅ |
| Transaction currency = account currency | **REST handler** | `transactions.go:180-183` (create) & `:353` (update) | ❌ REST-only → must port |
| Category type compatible with transaction type | **REST handler** | `transactions.go:198` ("Category type must match transaction type") | ❌ REST-only → must port |
| Category parent: same type | **REST handler** | `categories.go:120` ("Parent category must be the same type") | ❌ REST-only → must port |
| Category hierarchy ≤ 2 levels | **REST handler** | `categories.go:127-128`, `:302-303`, `:309-315` (`HIERARCHY_LIMIT_EXCEEDED`) | ❌ REST-only → must port |
| Category no cyclic/self parent | **REST handler** | `categories.go:275` (`*req.ParentID == categoryID` guard) | ❌ REST-only → must port |
| Category name uniqueness (active) | **DB partial unique index** | `idx_categories_unique_active` on (family_id,type,name,COALESCE(parent_id)) WHERE is_active (migr 004) | ✅ below (but surfaces as raw pg error) |
| Block delete account w/ transactions | **REST handler** (decision) + repo helper | `accounts.go:286` calls `HasTransactions`; block decision in handler | ⚠️ helper below, decision in REST |
| Block delete category w/ children/transactions | **REST handler** (decision) + repo helpers | `categories.go:309`/`:384` (`HasChildren`/`HasTransactions`) | ⚠️ helper below, decision in REST |
| Soft-delete columns `is_active` | **DB** | present in accounts (migr 003 l.19), categories (migr 004 l.17), transactions (migr 005 l.22) | ✅ |

## 4.1 ADR-2 verdict

- **Reused as-is (rule below handler):** balance recalc (trigger), category active-name
  uniqueness (partial index), all enum/amount/date CHECKs, soft-delete. gRPC handlers get
  these for free.
- **Currently in REST handler (blocks a thin gRPC handler):** initial_balance ≥ 0; tx
  currency = account currency; category-type = tx-type; category parent-type / hierarchy ≤ 2 /
  no-self-parent; delete-dependency guards; **and the entire Reports aggregation**. For these,
  a thin gRPC handler is **impossible** without first extracting a shared service/use-case
  layer (or duplicating the checks). **→ R2.**
- **Missing entirely:** account name uniqueness — must be decided & implemented (DB unique
  partial index vs service check) before either API can claim the rule.

# 5. Error Mapping

| Aspect | Finding |
|--------|---------|
| Domain→gRPC status helper | **None.** Existing gRPC handlers inline `status.Errorf(codes.Internal, ...)` / `codes.Unauthenticated` (e.g. `grpc/handlers/accounts.go:27,32,39`). No central mapper. |
| Repository error style | **Inconsistent.** Sentinels only in `users.go`: `ErrInvalidCredentials`, `ErrUserNotFound`, `ErrEmailExists` (`internal/repository/users.go:17-19`). Account/Transaction/Category repos return **raw pgx/sqlc errors**; not-found detected by string `err.Error() == "no rows in result set"` (`categories.go:170,183`). Duplicate (pg `23505`) handled only in `users.go` Register. |
| REST → HTTP mapping | Manual per-handler via `writeError(w, http.StatusXxx, CODE, msg)` → envelope `dto.NewErrorResponse(code, message, details)` `{success:false, error:{code,message,details}}`. Examples: 404 `NOT_FOUND` (`accounts.go:162…`), 400 `VALIDATION_ERROR` (+`details[]`), 400 `HIERARCHY_LIMIT_EXCEEDED`, 409-style conflict for email only. Not-found is mapped from **any** error after `GetByID` (so a real DB error is masked as 404 — fragile). |

**Implication:** for gRPC/REST parity we must introduce sentinel domain errors (at least
`ErrNotFound`, `ErrAlreadyExists`, `ErrValidation`, `ErrConflict`) shared by both layers, plus
one `func toStatus(error) error` (gRPC) mirroring the REST code map:
`NotFound→codes.NotFound`, `AlreadyExists→codes.AlreadyExists`,
`Validation→codes.InvalidArgument`, dependency conflict→`codes.FailedPrecondition`,
unauth→`codes.Unauthenticated`, else `codes.Internal`.

# 6. proto ↔ DB ↔ REST-DTO Discrepancies

## 6.1 Account

| proto field (accounts.proto) | type | DB column (accounts) | REST DTO | Discrepancy |
|---|---|---|---|---|
| id | string | id uuid | id | uuid↔string (OK via .String()) |
| name | string | name varchar | name | — |
| type | string | type varchar (CHECK) | type | — |
| currency | string | currency varchar (CHECK) | currency | — |
| balance | **double** | `current_balance` numeric(15,2) (+`initial_balance`) | balance/initial_balance (decimal) | ⚠️ **name** (proto `balance` vs DB `current_balance`); ⚠️ **money as double** (precision loss vs numeric/decimal); proto exposes one balance, DB has two |
| description | string | description text (nullable) | description | ⚠️ proto bare string can't express NULL |
| is_active | bool | is_active bool | is_active | — |
| created_at/updated_at | Timestamp | timestamp | RFC3339 | — |
| (none) | — | family_id uuid | (none) | OK — scoped by JWT context |
| (none) | — | initial_balance | initial_balance (create/update input) | ⚠️ not in proto Account; needed in CreateAccountRequest |

## 6.2 Transaction

| proto field | type | DB column | Discrepancy |
|---|---|---|---|
| amount / amount_base | **double** | numeric(15,2) | ⚠️ money as double (precision) |
| currency / base_currency | string | currency varchar; base_currency is constant "RSD" | base_currency not a column (derived) |
| date | string | transaction_date date | string↔date (format contract needed) |
| category_name | string | (joined, not a column) | derived via join |
| account_id/category_id | string | uuid | uuid↔string |
| (none) | — | family_id, created_by, is_active | not surfaced (context/audit) |

## 6.3 Category / Report

- **Category:** no proto yet. DB: id, family_id, name, type, parent_id (nullable uuid),
  is_active. Proto must model `parent_id` as **optional** (NULL = root) and carry a
  clear-parent signal for Update.
- **Report:** no proto yet. REST DTOs (`SpendingByCategoryResponse`, `MonthlySummaryResponse`)
  use string-decimal money + maps (`income_breakdown map[string]decimal`). Proto has no native
  decimal; mapping decimal→string or double must be decided (consistency with money-as-double
  risk above).

**Cross-cutting:** money is `double` in existing protos but `numeric`/`decimal` in DB/REST.
This is a precision risk for the new financial RPCs — decide string-decimal vs double once,
consistently (see R-money).

# 7. Open Spec Questions (§8): Answers

1. **Do Update* protos use proto3 optional / wrappers for partial update?**
   **N/A → must be created.** No Update* messages exist. Decision: **yes, use `proto3
   optional`** on all mutable fields to match the existing pointer-based partial updates
   (+ explicit clear-parent for categories). See R1.
2. **Are the required protos (categories/reports/auth) present?**
   **No.** Three proto files are missing and must be authored; only List RPCs exist for
   accounts/transactions.
3. **Do interceptors cover new services automatically?**
   **Yes.** The logging+auth chain is global on the `grpc.Server`; new services are covered
   with no extra wiring. (Add a `UserIDFromContext` accessor for tx audit.)
4. **Do repository functions exist for all 14 methods with matching sqlc return types?**
   **Mostly yes** (see §3). Two caveats: `Transaction.Delete` needs `deletedBy`; **Reports
   have no single repo function** — aggregation lives in REST.
5. **Is there a shared domain→status error mapper and consistent domain errors?**
   **No.** Only `users.go` has sentinels; no gRPC mapper. Must build both for parity.

# 8. Decisions Required Before Implementation

- **R1 — proto3 optional on Update\*:** author `Update{Account,Category,Transaction}Request`
  (and Create*/Delete*) with `proto3 optional` (or wrappers) on every mutable field;
  categories need an explicit clear-parent field. Without this, partial update silently
  breaks (zero-value vs unset).
- **R2 — rules currently in REST handlers:** initial_balance ≥ 0, tx currency = account
  currency, category-type = tx-type, category parent-type/hierarchy≤2/no-self, delete-guards,
  and **all Reports aggregation** live in REST. Decide: **(a)** extract a shared
  service/use-case layer reused by both REST and gRPC (recommended — keeps handlers thin and
  rules single-sourced), or **(b)** duplicate checks in gRPC (fast but drift-prone). Thin
  gRPC handlers are not possible for these without (a).
- **R3 — trigger behavior on soft-delete:** **OK, no change needed.** The balance trigger
  fires on UPDATE and the recalc excludes `is_active=false` rows, so soft-deleting a
  transaction correctly updates the account balance. Reuse as-is.
- **R-err (error mapping):** introduce shared sentinel domain errors
  (`ErrNotFound`/`ErrAlreadyExists`/`ErrValidation`/`ErrConflict`) and a single
  `toStatus(err) error` for gRPC mirroring the REST code map; replace string-matched
  not-found. Required for REST/gRPC parity.
- **R-uniq (account name):** account name uniqueness is unimplemented — decide DB partial
  unique index (mirrors categories) vs service-layer check, and which error/code it raises.
- **R-money:** money is `double` in existing protos but `numeric`/`decimal` in DB/REST.
  Choose string-decimal vs double for all financial proto fields **once**, consistently, to
  avoid precision loss in the new RPCs.
